# 容量与降级手册 — 单实例 512MiB 常驻内存预算

适用对象：Voice Timeline Renderer 单实例部署。本手册回答一个问题：**在单实例常驻内存（RSS）预算 512MiB 下，哪些负载组合可以承诺交付，哪些必须降级或拒绝。**

- 证据基线：`docs/capacity-evidence/capacity-canonical.json`（16 个隔离场景全量数据）
- 代码基线：git `37a64934`，生产实现零改动（见 §10）
- 测量工具：`cmd/capacitycheck`（新增，非生产代码），真实 `cmd/voiceservice` 子进程 + 独立数据目录 + `/proc` 内核高水位（VmHWM）
- 测量环境：linux/arm64，10 CPU，主机内存 7934MiB，go1.23.12。512MiB 是部署目标，通过对未受限进程实测 VmHWM 对照判定
- 数字为单次运行实测；运行间抖动通常 ±10%，个别场景可达 ±15–20%（例：2 并发登记两次实测 333.1 / 271.5MiB，16 源满帧渲染两次实测 367.0 / 312.3MiB）。384MiB 承诺线（预算的 75%）即为吸收该抖动而设

---

## 1. 判定规则（先读这个）

| 判定 | 标准 | 含义 |
|---|---|---|
| **可承诺 commit** | 实测 VmHWM ≤ 384MiB（预算的 75%），且全部渲染任务终态 `completed`，且下载输出摘要与回执一致 | 可作为常态负载承诺 |
| **边界 boundary** | 384MiB < VmHWM ≤ 512MiB，功能事实全部正常 | **不是常态承诺**。只允许隔离运行（不同时叠加其它大负载），并部署 RSS 监控 |
| **缺口 gap** | VmHWM > 512MiB，或任务未达 `completed`，或下载/摘要失败，或服务目标未达成 | 不得作为部署组合上线，必须降级 |

两条反自欺规则，贯穿全册：

1. **"进程没崩溃"不等于"组合可上线"**。缺口 G1 中渲染任务终态是 `completed`、输出可下载、摘要匹配——但峰值 RSS 870.4MiB，是预算的 1.70 倍。进程活着不是交付证据。
2. **"单个请求成功"不等于"组合可上线"**。缺口 G3 中 4 个并发登记全部返回 201——但峰值 RSS 580.4MiB 超预算。每个请求都成功，组合仍然不可交付。

所有判定以**最终任务状态 + 下载事实 + 内核内存高水位**为准，不以"请求没报错"为准。

## 2. 配置上限各自约束的阶段

这些上限**分别**约束流水线的不同阶段，任何一个都不能代表其它阶段的压力：

| 上限 | 值 | 约束阶段 | 位置 |
|---|---|---|---|
| `MaxSourceRequestBytes` | 48MiB | HTTP 请求体（源登记的 base64 JSON） | `httpapi` |
| `MaxJSONBytes` | 2MiB | 时间线/渲染请求体 | `httpapi` |
| `MaxSourceBytes` | 32MiB | 解码后的单个素材 WAV 字节 | `service` |
| `MaxSpans` | 64 | 单时间线片段数 | `domain` |
| `MaxOutputFrames` | 8,640,000（48kHz 下 180s） | 时间线输出总帧数（编排与渲染双重检查） | `domain`/`render` |
| `ReadHeaderTimeout` / `ReadTimeout` | 5s / 60s | 请求头与整个请求体的到达时限 | `cmd/voiceservice` |
| `WriteTimeout` / `IdleTimeout` | 180s / 60s | 响应写出总时限 / 空闲连接 | `cmd/voiceservice` |

与内存相关的四个架构事实（来自代码，均经实测验证）：

1. **服务层一把互斥锁串行化所有写操作与渲染**（`service.Service.mu`）：登记、编排、渲染逐个执行；读取（`GetSource`/`GetTimeline`/`GetRender`/`GetReceipt`/`GetOutput`）不经过该锁。
2. **渲染在 `PUT /v1/renders/{id}` 请求内同步完成**：响应返回时渲染已结束；`WriteTimeout=180s` 是渲染+响应的总上限。
3. **HTTP 层在锁之外**：每个在途登记请求的 base64 字符串（≈1.33×素材字节）在排队等待锁期间就已占用内存——并发上传的内存会**相乘**，即使处理是串行的。
4. **渲染把全部引用素材整体载入内存**：按"不同素材 ID"去重后，所有 WAV 字节常驻到渲染结束；解码为 float32 再翻倍；回执构建时还会把输出再解码一遍。`GET /v1/renders/{id}/output` 每次把整个输出文件读入内存。

## 3. 内存模型（为什么组合判断不能靠"单个上限都通过"）

各阶段峰值占用的估算构成（PCM16 → float32 使采样数据翻倍）：

- **登记单个 S 字节素材** ≈ 1.33·S（base64 JSON 串）+ 1·S（解码载荷）+ 2·S（float32 采样）≈ **4.3·S** + 运行时基线。实测 32MiB 素材 → 225.2MiB。
- **渲染** ≈ Σ（不同素材 WAV 字节）×1（原始字节常驻）+ Σ×2（解码副本）+ 输出帧×声道×4B（片段剪辑）+ 输出帧×声道×4B（混音缓冲）+ 输出帧×声道×2B（编码输出）+ 输出帧×声道×4B（回执再解码）+ GC 余量。
- **并发登记**：N 个在途请求 × 各自 1.33·S 的 HTTP 层占用 + 一份 4.3·S 的锁内工作集。
- **并发下载**：N × 输出字节（每次 GET 全量读入内存）。

由此得到规划估算式（实测校准，误差 ±15%）：

```
渲染峰值估算 ≈ 3 × Σ(不同素材字节) + 14B × 输出帧 × 声道数 + 64MiB 运行时基线
```

| 校验点 | 估算 | 实测 VmHWM |
|---|---|---|
| 2×32MiB 素材，8.60M 帧立体声 | 497MiB | 497.3MiB |
| 64×4MiB 素材，2.30M 帧立体声 | 894MiB | 870.4MiB |
| 1×32MiB 素材，8.39M 帧立体声 | 395MiB | 459.7MiB |
| 16×1MiB 素材，8.32M 帧立体声 | 345MiB | 312.3MiB |
| 64×1MiB 素材，4.31M 帧立体声 | 377MiB | 367.7MiB |

**结论**：`MaxSourceBytes=32MiB`、`MaxSpans=64`、`MaxOutputFrames=8.64M` 各自单独成立时实例都能存活（§5.1），但"64 个片段 × 每片段一个大素材 × 满帧输出"的组合需要数倍于预算的内存。判断组合是否可交付必须过 §3 的估算式并对照 §1 的判定带，不能逐项打勾。

## 4. 实测方法（可复现）

```bash
# 全量 16 场景（约 4 分钟，含一个 60s 的超时场景）
go run ./cmd/capacitycheck -out docs/capacity-evidence/<new-run>.json
# 单个场景
go run ./cmd/capacitycheck -only render-two-max-sources -out /tmp/one.json
```

- 每个场景启动一个**全新的生产服务器子进程**（`cmd/voiceservice` 默认参数，未改一行代码），使用独立临时数据目录，经真实 HTTP 驱动。
- 内存取 `/proc/<pid>/status` 的 **VmHWM**（内核维护的 RSS 高水位，无采样遗漏），辅以 10ms 轮询 VmRSS。
- 每个渲染场景核对：任务终态（轮询 `GET /v1/renders/{id}` 至 `completed`/`failed`）、回执摘要、下载输出的 SHA-256 与回执一致性。
- 前提：Go 1.23+、Linux `/proc`；不需要网络与外部服务。

## 5. 实测结果与可承诺组合

### 5.1 上限单维生效证据（场景 `limits-enforcement`，峰值 276.3MiB）

| 检查 | 结果 |
|---|---|
| 素材恰好 32MiB | 201 接受（登记耗时 340.9ms） |
| 素材超 1 帧 | 413 `source_too_large` |
| 请求体 ~49.4MiB（超 48MiB） | 413 `request_too_large` |
| 65 个片段 | 422 `invalid_span_count` |
| 输出超上限 1 帧 | 413 `timeline_too_long`（编排期拒绝，无需渲染） |

即：每个上限**单独**都按稳定错误码生效。这只是组合判断的起点，不是终点。

### 5.2 可承诺组合（commit）

| 组合 | 实测 VmHWM | 关键延迟 | 任务/下载事实 |
|---|---|---|---|
| 普通负载：3×1MiB 素材、2 片段、31,200 帧输出 | 18.8MiB | 登记 1MiB 14–17ms；渲染 PUT 12ms | `completed`，摘要匹配 |
| 单素材上限登记：1×32MiB | 225.2MiB | PUT 320.3ms（请求体 44.7MiB） | 读回摘要一致 |
| 小素材拼接近满帧输出：16×1MiB → 8,316,256 帧（上限的 96%） | 312.3MiB | 渲染 PUT 298ms | `completed`，摘要匹配 |
| 片段上限：64 片段 × 64 个 1MiB 素材 → 4,305,600 帧 | 367.7MiB | 渲染 PUT 247ms | `completed`，摘要匹配 |
| 2 并发满尺寸登记（2×32MiB） | 271.5MiB | 末位 437ms | 全部 201 |
| 4 并发下载 32MiB 输出（独立实例实测） | 138.9MiB | 单次 56–82ms | 4 份下载摘要均与回执一致 |

### 5.3 边界组合（boundary：只允许隔离运行 + RSS 监控，不得再叠加并发）

| 组合 | 实测 VmHWM | 距预算余量 | 关键事实 |
|---|---|---|---|
| 单素材满帧输出：1×32MiB → 8,388,597 帧 | 459.7MiB | 52.3MiB | 渲染 PUT 319ms，`completed`，摘要匹配 |
| 双满素材：2×32MiB → 8,595,200 帧 | 497.3MiB | **14.7MiB** | 渲染 PUT 370ms，`completed`，摘要匹配 |
| 3 并发满尺寸登记 | 491.5MiB | **20.5MiB** | 末位 548ms，全部 201 |
| 大渲染期间叠加读写（2×16MiB 渲染中） | 435.1MiB | 76.9MiB | 读 0.5ms 不阻塞；竞争写等待 204.1ms |
| 渲染+下载同实例（渲染后 4 并发下载） | 459.4MiB | 52.6MiB | 下载阶段隔离实测仅 138.9MiB |

这些是**保留的合法近上限制作路径**：不需要为了安全去统一调小 `MaxSourceBytes`/`MaxSpans`/`MaxOutputFrames`——每个维度都有可交付的近上限路径。但边界组合必须独占实例：余量最小的两个（14.7MiB、20.5MiB）叠加任何并发都会越界。

### 5.4 缺口组合（gap：不得上线；证据可追到最终任务与下载事实）

| 缺口 | 组合 | 实测事实（证据场景） |
|---|---|---|
| **G1** | 64 片段 × 64 个不同 4MiB 素材（Σ256MiB）→ 2.30M 帧 | 任务 `rnd_mid_over` 终态 `completed`，输出 9,216,044B 可下载且摘要匹配——**单请求完全成功**；但 VmHWM **870.4MiB** = 预算 1.70×（`render-many-mid-sources-overbudget`） |
| **G2** | 同 G1，但给进程设置 `GOMEMLIMIT=460MiB` | 任务仍 `completed`、输出仍可下载，VmHWM 仍达 **814.1MiB**：Go 软内存目标**不能**当作 512MiB 预算的执行手段（`render-many-mid-sources-capped`） |
| **G3** | 4 并发满尺寸登记（4×32MiB） | 4 个请求**全部 201**；VmHWM **580.4MiB** 超预算（`concurrent-max-registrations-4`）。并发边界实测：2→271.5MiB（commit），3→491.5MiB（临界），4→580.4MiB（缺口） |
| **G4** | 40MiB 请求体以 0.5MiB/s 上传 | 60,001ms 时服务器 `ReadTimeout` 截断读取，处理器把截断的 JSON 映射为 **422 `invalid_json`**（不是连接重置）；素材未持久化（`GET` → 404 `source_not_found`）（`slow-upload-read-timeout`） |
| **G5** | 渲染进行中进程被 SIGKILL（平台硬限制/OOM 的代理） | 重启后任务永远停在非终态 `"rendering"`；输出与回执 409 `render_not_completed`；同一 render id 幂等重放返回 200 但仍是 `"rendering"`（**id 楔死，无法复活**）；换新 render id 后同一时间线渲染 `completed` 且下载正确（`crash-mid-render-stale-job`） |

## 6. 普通路径的等待说明（可信预期）

以下均为规范运行实测（空闲实例，本机 loopback；部署到其它环境应按 §4 复测校准）：

| 操作 | 等待预期 |
|---|---|
| 登记 1MiB 素材 | 14–17ms |
| 登记 32MiB 素材（最大合法） | ~320ms（请求体 44.7MiB） |
| 详情读取（源/时间线/任务/回执） | p50 ≈ 0.10–0.16ms，p95 ≤ 0.23ms；**渲染进行中不劣化**（实测 0.5ms，读取不走服务锁） |
| 渲染（同步，PUT 即结果） | 31,200 帧 → 12ms；4.3M 帧 → 247ms；8.4M 帧 → 319ms；8.6M 帧 → 370ms。客户端超时建议 ≥5s（10× 余量）；服务端 `WriteTimeout=180s` 兜底 |
| 上传速率下限 | 最大合法请求 48MiB 必须在 `ReadTimeout=60s` 内到达 → **持续 ≥0.8MiB/s**；更慢会在 ~60s 收到 422 `invalid_json`（G4 签名） |
| 并发写排队 | 写操作串行：第 N 个并发大登记末位延迟 ≈ N×单个（2 并发末位 437ms，3 并发 548ms，4 并发 671ms） |
| 渲染期间提交写 | 等待 ≈ 渲染剩余时长（实测写等待 204.1ms，渲染总时长 327.9ms） |
| 下载 32MiB 输出 | 56–82ms（4 并发下） |

## 7. 服务目标核对与缺口登记

| 服务目标 | 结论 |
|---|---|
| 普通登记与详情读取有可信等待说明 | **达成**（§6 实测分布） |
| 各上限单维生效且错误码稳定 | **达成**（§5.1） |
| 每个上限维度保留可交付的近上限制作路径 | **达成**（§5.2/§5.3；单素材满帧、64 片段、满帧输出均可交付，部分为边界级） |
| 上限的任意组合都可交付 | **未达成 → 缺口 G1、G3**（多素材×大素材、4 并发满尺寸登记超预算） |
| 512MiB 预算可由进程内软限制执行 | **未达成 → 缺口 G2**（GOMEMLIMIT 不约束 RSS 高水位，实测软限下仍 814.1MiB） |
| 超时行为可解释、素材不留残迹 | **达成但签名反直觉 → 缺口 G4 记录**（ReadTimeout 表现为 422 `invalid_json`；素材未持久化已验证） |
| 进程被杀后渲染任务终态化/可恢复 | **未达成 → 缺口 G5**（陈旧 `"rendering"` + id 楔死；只能换新 id） |

## 8. 降级手册（信号 → 判断 → 动作）

| 信号 | 判断 | 动作（不改生产配置） |
|---|---|---|
| 需要渲染"多不同素材 × 大素材"的时间线 | 用 §3 估算式：Σ不同素材字节 ≤16MiB 可承诺；≤64MiB 仅边界（隔离运行）；>64MiB 不承诺（G1） | 拆成多条时间线分别渲染、在服务外拼接；或减少单时间线引用的不同素材总字节；或提高实例内存预算 |
| 上传在 ~60s 时收到 422 `invalid_json` | 这是 `ReadTimeout` 签名（G4），**不是素材损坏**；`GET` 该源应为 404 | 把上传提速到 ≥0.8MiB/s（最大请求 48MiB/60s），或减小单素材；确认 404 后重发 |
| 需要并发登记大素材 | 实测：2 并发 commit（271.5MiB），3 并发临界（491.5MiB），4 并发缺口（580.4MiB） | 客户端串行化大素材上传；至多 2 并发；不要为并发调小 `MaxSourceBytes` |
| 渲染期间登记/编排变慢 | 预期行为：写操作在服务锁上排队（§6） | 把写操作排到渲染间隙；详情读取随时可用，无需降级 |
| 进程被平台硬限制杀死（OOM 等） | 渲染任务不会自动终态化：永远停在 `"rendering"`，输出/回执 409，id 楔死（G5） | 运维动作：**换新 render id 重试**（实测可完成）；不要幂等重放旧 id（返回陈旧记录）；把该 id 标记为废弃 |
| 想用 `GOMEMLIMIT` 执行 512MiB 预算 | 无效：实测软限下 RSS 仍 814.1MiB（G2） | 需要硬执行时用平台级限制（cgroup `memory.max`），并接受 G5 的崩溃语义；否则按 §5 的组合表控制负载 |
| 边界组合要上线 | 余量最小仅 ~15–21MiB（双满素材 14.7MiB、3 并发登记 20.5MiB） | 独占实例、禁止叠加任何并发、部署 RSS 监控与重启预算；否则降级到 §5.2 的 commit 组合 |

## 9. 维护与复测

- 任何上限值、渲染管线或运行时被修改后，重跑 §4 的规范套件并更新本手册的实测列。
- 估算式（§3）用于规划；判定只用实测 VmHWM 对照 §1 判定带。估算落在判定带 ±15% 边缘时按更严一档处理。
- 证据文件是判定的唯一依据：每个场景的每步状态码/延迟/错误码、任务终态、回执与下载摘要都在其中，可逐条复核。

## 11. 免责与边界

- 测量在 linux/arm64、10 CPU、7934MiB 主机上完成；512MiB 为部署目标，未经真实 cgroup 硬限制环境复测（G5 用 SIGKILL 代理硬限制语义）。
- 素材为合成正弦波；内存占用由帧数与声道决定，与音频内容无关，结论对真实语音成立。
- 单次运行、本机 loopback；延迟数字用于量级判断，部署前应在目标环境复测。
- 本手册不覆盖：磁盘容量与 inode 预算、长期运行的碎片/泄漏趋势、多实例编排。
